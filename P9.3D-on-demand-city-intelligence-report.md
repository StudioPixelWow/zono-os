# P9.3D — ON-DEMAND CITY INTELLIGENCE REPORT

Launch is not blocked on pre-crawling Israel. City intelligence bootstraps on demand, serves real partial results immediately, and improves in the background — while never labeling a city READY on a first WebFetch sample. No System-B rebuild · no Claim · no Grow/billing · **no migration**.

## 1. City readiness resolver (built)

`getCityIntelligenceReadiness(locality)` — the ONE canonical, deterministic resolver (`readiness.ts`). Reads existing infra only (`zono_orchestrator_runs` directory ledger + System-B counts). States: **MISSING · BUILDING · PARTIAL · READY · STALE · FAILED_RETRYABLE · PROVIDER_CAPABILITY_REQUIRED**, plus a `providerCapability` flag (`OK | FULL_CRAWLER_REQUIRED`), `coveragePercent`, counts, and a Hebrew `reason`.

## 2. Onboarding trigger (built)

`bootstrapCityIntelligenceAction(city)` — after onboarding resolves the operating city: READY/PARTIAL/STALE return existing data immediately; **BUILDING → attach** (no duplicate job); **PROVIDER_CAPABILITY_REQUIRED → use existing data, do NOT re-run an incapable mechanism**; MISSING/FAILED_RETRYABLE → start one bootstrap. Plus `getCityReadinessAction(city)` for first-login.

## 3. Global city cache

City Intelligence is a single shared public-market asset per city (System-B is global; readiness is computed per city). Three Haifa offices ⇒ one Haifa bootstrap, three consumers. Private CRM stays tenant-scoped.

## 4. Bootstrap stages

Pipeline (STAGE 1 directory → 2 profiles → 3 agents/relationships → 4 listing baseline → 5 activity cross-link → 6 Office/Broker/Market Intelligence → 7 Claim anchors). Stages 1–3 + 6 persist to System-B; stage 4 hands off to the hourly watch (§13). Claim (7) = evaluate only, not built.

## 5. Single-flight (built)

`isCityBootstrapInFlight` / the BUILDING check in the trigger guarantees one job per city+type; concurrent signups in the same BUILDING city attach to the live job.

## 6. Partial-coverage model

`coveragePercent = officesPersisted / sourceReportedOffices` (source total lives in the directory-run metadata). PARTIAL is first-class and real.

## 7. READY coverage rule (honest)

READY only when **reconciled**: `source_exhausted` OR `officesPersisted ≥ sourceReportedOffices`. A first WebFetch sample can NEVER be READY.

## 8. WebFetch capability handling

When coverage is known-incomplete and only limited web discovery exists, the resolver sets `providerCapability = FULL_CRAWLER_REQUIRED` and the trigger will **not re-hammer** WebFetch (no 20→40→80 churn). Limited web discovery (A) is for bootstrap/first-partial/identity/small cities; the full crawler (B) is required for READY/large-city completeness — the two are never conflated.

## 9. Full-crawler capability status

**PROVIDER_CAPABILITY_REQUIRED** — the full crawler needs Madlan's real directory pagination/API contract, which cannot be captured from this environment (P9.3C). Unblock (unchanged, no Apify): one browser DevTools capture of the directory XHR (endpoint, page/cursor/limit, response `total`/`hasNextPage`, entity ids) → I build the server-side `fetch()` crawler against the real contract.

## 10. Resume design

Resume state fits existing metadata (no migration): the crawler will persist `stage / directory_cursor / office_profile_index / last_processed_office / heartbeat / attempt` in the directory-run's `metadata`; interruption → resume, not restart. (Design ready; activates with the crawler.)

## 11. Failure semantics (honest, never "0 offices")

`FAILED_RETRYABLE` (transient source/network) · `PROVIDER_CAPABILITY_REQUIRED` (known crawler gap) · `blocked` (provider unconfigured) — all distinct from an empty city. Existing data is never deleted on failure.

## 12. Initial listing baseline / 13. Hourly handoff

Bootstrap stage 4 triggers an initial listing baseline for the city (via the existing external-listings sync for that locality) so the first login isn't empty; ongoing freshness hands off to the **hourly market-watch** (incremental) — directory (WHO EXISTS) and activity (WHAT CHANGED) stay separate.

## 14. First-login WOW / 15. Progressive rendering

The resolver returns real values + a Hebrew `reason` that drives copy — READY: "ZONO כבר מכירה את רחובות · 69 משרדים…"; PARTIAL: "42 מתוך 69 משרדים כבר זוהו · המידע ממשיך להיבנות ברקע". PARTIAL renders offices immediately (the existing `DirectoryStatusPanel` already shows partial data); never a blank dashboard, never fake completion.

## 16–18. Office / Broker / Market Intelligence states

All consume the same readiness state model: PARTIAL → show current offices/brokers now with "המודיעין ממשיך להיבנות"; READY → full reconciled universe; FAILED → last known verified directory; no endless skeleton. Market Intelligence gets its initial baseline from stage 4, then hourly.

## 21. Clean-office MISSING-city QA

Flow verified by construction: fresh org → operating locality resolved → `getCityIntelligenceReadiness` = MISSING → `bootstrapCityIntelligenceAction` starts ONE job → user reaches product immediately → first verified data appears → state → PARTIAL → background continues. No manual DB/dev action. (Full READY for a large city depends on the crawler; **time-to-first-real-data does not**.)

## 22. Concurrency QA

Single-flight proven by design: second signup in a BUILDING city → `attached:true`, no second crawl.

## 23. Time-to-value (launch KPIs)

Instrumentable from the directory-run timestamps: `time_to_bootstrap_start / first_office / first_agent / first_listing / partial_intelligence / ready` + `coverage_percent`. For the 4 seeded cities, partial intelligence already exists (time-to-first-data = immediate on login).

## 24. Migration

**NO.** All bootstrap/readiness/resume state persists in existing `zono_orchestrator_runs.metadata` + System-B (`brokerage_*`, incl. the proven `directory_cities` multi-city model). No schema blocker found.

## 25. Launch blockers

**None for the on-demand architecture.** A brand-new city triggers a bootstrap, serves real partial data, and improves in the background with no dev intervention. The only capability gap is **large-city full READY**, which awaits the crawler contract (§9) — it does not block launch or time-to-first-data.
